# Промпт: Глубокое изучение метаданных проекта админ панели

Универсальный промпт для Claude Code. Запусти в чистой сессии в корне проекта
админ панели — получишь полный контекст для последующей работы.

---

```
Сделай глубокое изучение метаданных проекта без агентов — без `Agent`, без скиллов
типа research/sync-vault. Только Read/Bash/Glob/Grep. Цель — построить полную карту
проекта, чтобы в последующих запросах в этом сеансе у тебя был полный контекст.

═══════════════════════════════════════════════════════════════════════════════
ОБЛАСТЬ ИЗУЧЕНИЯ — все артефакты «о проекте», а не код приложения:
═══════════════════════════════════════════════════════════════════════════════

1. ИНСТРУКЦИИ И ПРАВИЛА
   • Все CLAUDE.md, AGENTS.md, .cursorrules, .windsurfrules (рекурсивно)
   • README.md / STRUCTURE.md / ARCHITECTURE.md / CONVENTIONS.md / ONBOARDING.md
     на каждом уровне дерева
   • CONTRIBUTING.md, CODE_OF_CONDUCT.md, SECURITY.md, CHANGELOG.md
   • LICENSE, NOTICE
   • Все ADR / SPEC / RFC / BRD / FRD / TRD (поиск по docs/, .docs/, doc/, design/)

2. КОНФИГИ ЗАВИСИМОСТЕЙ И ИНСТРУМЕНТАРИЯ
   • package.json (все), package-lock.json, pnpm-lock.yaml, yarn.lock, bun.lockb
   • tsconfig*.json, jsconfig.json, eslint.config.*, .eslintrc*, .prettierrc*
   • vitest.config.*, jest.config.*,
     playwright.config.*, tailwind.config.*, postcss.config.*, next.config.*,
     vite.config.*, webpack.config.*

3. ИНФРА И ДЕПЛОЙ
   • fly.toml, vercel.json, netlify.toml, render.yaml
   • .github/workflows/*.yml, .gitlab-ci.yml, bitbucket-pipelines.yml,
   • .pre-commit-config.yaml, lefthook.yml, husky/, lint-staged
   • .env.example, .env.sample, .env.template, .env / .env.local

4. КАРКАС КОДА (структура, не реализация)
   • Дерево директорий до глубины 3-4 уровня (через `find -type d`)
   • Подсчёты:
     – исходные файлы по языкам
     – тестовые файлы
     – миграции, роутеры, модули/слайсы/фичи/пакеты
   • Точки входа:  index.ts
   • Композиционный корень/ роутер-агрегатор

5. КОНТРАКТЫ И СТАНДАРТЫ
   • OpenAPI
   • Архитектурные fitness-тесты / boundary-проверки (важно прочитать!)
   • Code-style hooks, conventional commits, husky-hooks

6. СОСТОЯНИЕ РЕПОЗИТОРИЯ
   • git rev-list --count HEAD, git log --oneline -20
   • git branch -a (без бэкап-веток)
   • git status --short — что не закоммичено
   • Размеры компонентов (du -sh)
   • Дата последнего коммита по каждому крупному поддиректорию

═══════════════════════════════════════════════════════════════════════════════
ПРАВИЛА РАБОТЫ
═══════════════════════════════════════════════════════════════════════════════

• Параллель: запускай независимые Read/Bash в одном tool-call блоке.
  *.lock (кроме факта существования и размера).
• Лимиты на чтение: README/CLAUDE.md/STRUCTURE.md — целиком; package.json
  — целиком; ADR/SPEC — целиком; всё остальное — первые 80-150 строк, дальше по
  необходимости.

═══════════════════════════════════════════════════════════════════════════════
ВАЛИДАЦИЯ — ОБЯЗАТЕЛЬНО
═══════════════════════════════════════════════════════════════════════════════

После сбора метрик СВЕРЬ заявленное в документации с фактом:
  • Если README говорит «N модулей» — пересчитай ls / find и сравни.
  • Если CLAUDE.md перечисляет компоненты — проверь, что каждый существует.
  • Если упомянут файл/папка — `ls` его.
  • Если зафиксирован stack (Redux / RTK / Pillow / ...) — grep package.json /
    pyproject.toml.
  • Если есть архитектурный тест с MODULES = [...] — этот список авторитетен,
    README должен ему соответствовать.

Любое расхождение между документацией и кодом → подними флаг ЯВНО в финальном
отчёте, отдельной секцией «Документация vs реальность», с конкретными цифрами
и путями.

═══════════════════════════════════════════════════════════════════════════════
ФОРМАТ ИТОГОВОГО ОТЧЁТА
═══════════════════════════════════════════════════════════════════════════════

Дай отчёт в одном сообщении со следующими разделами (опускай пустые):

  1. Идентификация проекта — что это, в одном абзаце; домен; стадия
  2. Карта компонентов — таблица: путь, технология, порт, деплой
  3. Архитектурный стиль
  4. Cross-service communication — как сервисы общаются (диаграмма ASCII)
  5. Метрики — фактические цифры (commits, файлы)
  6. Tooling — пакетный менеджер, линтеры, форматтеры, type-checker, тест-раннер,
     pre-commit hooks, CI
  8. Конвенции — структура модулей/слайсов, naming, импорты, error envelope,
     auth модель
  9. Точки входа — какие файлы запустить, чтобы поднять/тестировать
 10. Документация vs реальность — расхождения, с пометкой severity (HIGH/MED/LOW)
 11. Технический долг и незакоммиченное — что в working tree, untracked, stale
     ветки, TODO/FIXME-плотность
 12. Контекст для будущих запросов — 5-10 пунктов, что АБСОЛЮТНО важно помнить
     при последующей работе (например: «pre-commit запускает ty, не mypy»;
     «admin-frontend в FSD, deep-imports запрещены»; «favorites — новый модуль,
     не упомянут в README»; «main-frontend — Next.js 16, see AGENTS.md»)

Финальный раздел №12 — самое ценное. Пиши его так, чтобы следующий запрос
читал его и сразу действовал правильно, без повторного исследования.

Не пиши промежуточных файлов, не сохраняй в vault. Один отчёт в чат. Точка.
```
